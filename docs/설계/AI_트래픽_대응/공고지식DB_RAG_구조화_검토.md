# AI 체인을 "공고 지식 DB + Jev + 청크 검색"으로 구조화하는 안 검토

> 작성 2026-11-24 Claude · **분석·설계 문서, 코드 미수정**. 근거는 현재 작업 폴더 코드와 로컬 풀 `web/.cache/pool-v1.json`(7,923건, 8.3MB)을 직접 확인한 결과다. 효과 수치는 기준선 측정 전이라 넣지 않았다.
> 관련: `Jev_적용범위_분기목록.md`, `Jev_판단모델_토큰절감.md`, `AI_토큰_최소화.md`

## 0. 결론

- 방향(공고 지식 DB + Jev 태그 + 원문 청크에서 필요한 부분만 꺼내 쓰기)은 장기 구조로 맞다. 다만 **"사용자 질문에 답하는 RAG 챗봇"이 핵심은 아니다.** 이 앱의 본업은 조건 판정(필터)이고, 비효율은 답변 생성이 아니라 **원문이 저장되지 않고, 파생 결과의 무효화 기준이 흩어져 있고, 일반 질문 경로의 근거 표본이 대표성이 없다**는 데서 나온다.
- **해커톤 일정 기준 판정: 전면 구조 전환은 반려, 최소 수정 4개만 조건부 추천.** 저장 형식·어댑터 전체·캐시·질문 흐름을 1인이 동시에 바꾸면 회귀 위험이 너무 크다(Codex 교차 검토 동일 판정). 전체 구조(2장)는 해커톤 이후 로드맵으로 둔다.
- 지금 할 최소 수정(4장): ① 기준선 측정 ② **본문 해시 기반 재분류**(지금은 제목이 같으면 태그를 그대로 물려받음) ③ 재시도 불가 오류는 공급자 폴백 중단 ④ 일반 질문 근거를 남은 후보 대표 표본으로.
- **벡터 DB는 넣지 않는다.** 7,923건, 질문 대부분이 분야·지역·대상 같은 정형 필터라 태그 필터 + 키워드로 충분하다.
- "RAG로 답변"이 실제로 필요한 곳은 공고 상세 Q&A 1곳뿐이고, 새 기능이라 효율화와 분리해 판단한다.

> Codex 교차 검토(`.ai-sync/tasks/20261124T101555-codex/result.md`) 반영: P1~P7 근거를 최신 코드에 맞게 좁힘(P5·P6·P7은 일부 이미 해결), 누락 문제 6개 추가, 결론을 "최소 수정만"으로 변경.

| P7 | **정확도 정답셋·전후 비교 기준 없음** | 공급자별 토큰·성공·실패 통계와 질문 피드백 저장은 있음 | 구조 변경 효과를 수치로 증명 못 함(심사 반박 지점) |

### 검토에서 추가된 구조적 문제
- 원문 섹션을 저장하면 8.3MB보다 크게 늘어남. Upstash 용량·명령 수·수집 시간·Vercel 실행 제한 계산이 없음.
- 출처마다 원문 제공 범위·형식이 달라 "자격/서류/근무지" 청크를 안정적으로 만들 수 있는지 미검증(출처별 원문 확보율 필요).
- Redis 조각과 meta 갱신 사이에 원자성이 없어 부분 실패 시 섞인 스냅샷이 생길 수 있음.
- 한국어 키워드 검색의 형태소·동의어·표 분해 품질 미검증.
- 삭제·마감·수정 공고의 파생 데이터 폐기(tombstone) 정책 없음.

## 2. 제안 구조

```
[수집 cron, 하루 1회]
 출처 API → 정규화 → 원문 섹션 청크 저장 (자격 / 지원내용 / 신청방법 / 제출서류 / 근무지 / 기간)
          → 변경 감지(원문 해시) → 바뀐 공고만 ↓
          → Jev 묶음 판정(분야·고용형태·주 대상·필수/우대·신청유형) ← 청크 중 필요한 섹션만 상태로
          → 규칙(나이·소득·날짜 숫자) → 조건
          → LLM은 규칙·Jev가 못 한 것만(상세 주소, 쉬운 요약) → 결과를 같은 레코드에 저장

[공고 지식 DB]  공고 1건 = { 정규화 필드, 청크[], 태그{값,확신도}, 조건[], 요약, 장소, 원문해시, 파생결과 버전 }
                 + 태그별 색인(분야·지역·대상·고용형태 → 공고 id 목록)

[대화 시점]
 질문 턴   : 서버가 색인으로 남은 후보 계산 → 정보량 큰 축 선택 → 템플릿/승격 풀 문장 (LLM 0)
             템플릿 없는 축만 LLM: 근거 = 남은 후보에서 축별로 고른 대표 청크(앞 4건이 아니라)
 결과 화면 : 요약은 DB에 이미 있음 (요청 시 재조회·재생성 없음)
 신청 준비 : 신청방법·서류 청크를 그대로 인용, 초안 LLM에는 해당 청크 + 사용자 사실 문장만
 공고 Q&A  : (4단계, 선택) 질문 → 그 공고 청크 중 키워드 일치 1~3개 → LLM이 인용해 답, 근거 없으면 "원문 확인"
```

### 저장소 선택

| 안 | 장점 | 단점 | 판정 |
|---|---|---|---|
| A. 지금 Upstash Redis 유지(현재 조각 저장 그대로) | 인프라 변경 없음 | 서버 조합 질의 불가. 공고별 키+Set 색인 전환은 7,923건 마이그레이션·명령 수 부담 | **데모까지 유지** |
| B. Postgres(Supabase 등) + 태그 컬럼 + 청크 테이블 + 전문 검색 | SQL 필터·통계·전문 검색, 나중에 pgvector | 새 서비스·마이그레이션, 마감 전 전환은 위험 | **장기 구조로 추천(해커톤 이후)** |
| C. 벡터 DB 전용 | 의미 검색 | 정형 필터가 본업이라 이득 작음, 한국어 임베딩 품질 검증 필요 | 지금은 반려 |

## 3. 시나리오

### S1. 새 공고 수집 (cron)
- 지금: 어댑터가 원문을 읽고 요약을 잘라 저장, 원문은 버림. 제목이 같으면 이전 태그를 그대로 물려받아 본문 변경이 반영 안 됨.
- 바뀐 뒤: 원문을 섹션 청크로 저장하고 원문 해시가 같으면 **아무 AI도 다시 안 부름**. 바뀐 공고만 Jev 1회(필요한 섹션만 상태로) + 규칙 + 꼭 필요한 LLM. 결과는 공고 레코드 한 곳에.
- 확인 지표: 실행당 AI 호출 수, 공고당 입력 토큰, 재계산 비율.

### S2. 질문 턴 ("서울 사는 구직자, 정보통신")
- 지금: 브라우저가 선택 분야 후보를 들고 축 분포를 계산해 보내고, 일반 질문 경로의 근거는 분야별 앞 4건. 승격 풀·캐시에 없으면 LLM이 약 1만 토큰 이상을 읽고 질문 생성.
- 바뀐 뒤: 서버가 색인으로 남은 후보 312건의 태그 분포를 계산 → "고용 형태"가 반반에 가깝게 나눔 → 템플릿 "어떤 형태로 일하고 싶습니까?" (LLM 0). 템플릿 없는 축일 때만 남은 후보에서 선택지별 대표 청크 2건씩 골라 LLM.
- 확인 지표: 질문 턴당 LLM 호출 비율, 턴당 후보 감소율(질문 품질).

### S3. 결과 카드 쉬운 요약
- 지금: 요약이 캐시에 없으면 `/api/summary`가 출처를 다시 조회하고 4초 안에 LLM 요약.
- 바뀐 뒤: 수집 때 지원내용 청크로 만든 요약이 레코드에 있음. 화면은 읽기만. 지연·재조회 없음.

### S4. 신청 준비 ("이 공고 서류 뭐 필요해?")
- 지금: 서류는 짧은 요약에서 단어 추출(`docsFromText`), 원문이 없어 놓치는 경우가 생김.
- 바뀐 뒤: "제출서류" 청크를 그대로 목록화하고 출처 배지로 인용. 초안 LLM에는 신청방법 청크 + 사용자 사실 문장만(지금 약 4,700자보다 작게).

### S5. (선택) 공고 상세 Q&A
- 사용자가 "휴학생도 돼요?"라고 물으면 그 공고의 자격 청크에서 키워드로 1~3개 찾음 → LLM이 **청크 인용으로만** 답, 청크에 근거가 없으면 "원문에 없음, 기관 확인 필요"로 고정 응답. 답변 캐시는 (공고, 질문 정규화) 키.
- 위험: 자격 판정을 Q&A가 엔진과 다르게 말할 수 있음 → 엔진 판정이 있는 속성(나이·지역·무주택 등)은 Q&A가 아니라 엔진 결과를 보여 줌.

## 5. 반려·보류한 것

- **벡터 임베딩 RAG 전면 도입**: 정형 필터가 본업이고 규모가 작아 이득 대비 인프라·검증 비용이 큼. 보류.
- **LLM이 자격 판정까지 답하는 챗봇**: 엔진(설명 가능·재현 가능)과 충돌, 오판 책임 문제. 반려.
- **수집 때 모든 공고를 LLM 요약**: 원문 해시 변경분만, 화면에 노출되는 공고 우선. 전수 LLM은 무료 한도 초과 위험.
