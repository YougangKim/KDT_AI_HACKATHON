## 1-1. 초안에서 바뀐 점 (Codex 교차 검토 반려 반영)

초안(Jev가 LLM 호출 여부를 결정, `status` 필드 추가, 직무 충돌 시 값 합치기)은 Codex 검토(`.ai-sync/tasks/20261124T103526-codex/result.md`)에서 **반려**됐다. 지적이 맞다고 판단해 아래처럼 고쳤다.
- Jev가 LLM을 건너뛰게 하면, 지금 LLM이 보완하던 지역·학력·고용 같은 비숫자 조건이 빠진다. 그러면 오탈락이 줄어드는 게 아니라 **대상이 아닌 공고가 "바로 신청"으로 통과**한다 → 1단계에서는 Jev를 **관찰만** 하고 결과에 반영하지 않는다.
- `status`는 엔진이 읽지 않아 장식이다 → 추가하지 않고 기존 `confidence: low`만 쓴다.
- 충돌을 모두 low로 내리면 "바로 신청"이 구조적으로 줄고, 직무 값 합치기는 무관한 직무를 통과시킨다 → 제외.

## 2. 1단계: 이번에 바꿀 것 (승인 요청 범위)

### ① 메모리 캐시 stale 수정
- `lib/sources/index.ts`의 `aiConditionCache`·`aiPending` 키를 `공고 id`에서 **`id + 구조화 프롬프트 버전 + 자격요건 원문 해시`**로 바꾼다.
- 이유: 같은 서버 프로세스 안에서 원문이 바뀌거나 프롬프트를 고쳐도 예전 조건을 붙이는 구멍이다. 대기 중 표시(`aiPending`)도 같은 키여야 바뀐 원문이 막히지 않는다.

### ② LLM 조건의 근거 구절을 원문과 대조
- LLM이 돌려준 조건의 `rawText`를 실제 자격요건 원문과 비교한다. 비교 전에 공백·문장부호를 지우고, 구절이 길면 앞 12자만 본다(부분 인용 허용).
- 원문에서 찾지 못하면 그 조건은 **`confidence: low`**로 낮춘다. 엔진에서는 탈락 대신 "확인 필요"가 된다.
- 이유: 지금은 LLM이 지어낸 구절도 근거처럼 보인다. "AI 생성만 있고 원문 근거가 없으면 unverified"를 기존 필드만으로 구현하는 최소 장치다. 영향받는 건 AI 해석 조건뿐이라 "바로 신청" 감소 폭은 작고, 6장에서 측정한다.

### ③ Jev 대상 판정 "관찰 모드"
- 수집 중(원문이 메모리에 있을 때) 자격요건 원문에 Jev 예/아니오 묶음 1회. 대상 8개(무주택 필수·1인 가구·대학생·구직자·재직자·신혼부부·수급자·청약통장)와 숫자 조건 존재 2개(나이 제한·소득 기준).
- **결과는 조건에 반영하지 않고** 원문 해시 키로 저장만 한다. 그리고 비교 스크립트가 "최종 조건(규칙+LLM)과 Jev가 얼마나 일치하는지", "Jev만 있었다면 LLM 호출을 몇 건 줄였을지", "그때 빠졌을 비숫자 조건이 몇 건인지"를 계산한다.
- 기본 OFF(`JEV_OBSERVE=1`일 때만). 실행당 상한을 둔다. 실패해도 기존 동작에 영향이 없다.
- 이유: 2단계(Jev로 LLM 줄이기)를 근거 없이 켜면 위의 오통과가 생긴다. 실제 공고로 측정한 숫자가 있어야 켤지 말지 정할 수 있다. 정답셋을 만들 기초 데이터도 된다.

## 2-1. 2단계 (측정 후 별도 승인)
- 관찰 결과에서 Jev와 최종 조건의 일치율이 높은 대상만 골라 LLM 생략 조건을 정한다. Jev만 찾은 조건은 버리지 않고 `low`(확인 필요)로 추가하는 안을 기본으로 한다.
- 전/후 고정 표본에서 오탈락·오통과·"바로 신청" 수를 비교해 회귀가 없을 때만 적용한다.

## 3. 구조 한눈에 (1단계)

```
[수집 cron]  어댑터 → 자격요건 원문(메모리)
   ├ 규칙: 나이·소득 숫자, 대상 단어                     (지금과 같음)
   ├ LLM: 지금과 같은 조건에서 호출                       (지금과 같음)
   │    └ 근거 구절을 원문과 대조 → 못 찾으면 confidence low   ← ②
   ├ 메모리 캐시 키 = id + 프롬프트 버전 + 원문 해시          ← ①
   └ (JEV_OBSERVE=1) Jev 대상 판정 → 저장만, 조건 반영 없음   ← ③
[측정 스크립트]  Jev vs 최종 조건 일치율, 줄일 수 있었던 LLM 호출 수, 빠졌을 비숫자 조건 수
```

## 4. 바꾸지 않는 것과 이유

| 항목 | 이유 |
|---|---|
| 요청마다 "DB 유사 검색 → Jev 충분성" | 이 앱의 요청은 공고 id·축 조합처럼 키가 정해져 있어 키 조회로 충분. 요청마다 Jev를 부르면 지연·비용만 늘어남 |
| 범용 `knowledge_items` 테이블, 임베딩 | 대상이 공고 하나, 필드 고정. 공고 레코드에 붙이는 쪽이 단순 |

| 공급자 체인 폴백 규칙 | 다른 공급자의 404(모델 없음)·400은 공급자별 문제라 다음으로 넘어가는 게 맞음. 절감 효과도 작음 |
| 다음 질문(next-question) 근거 표본 | 지금 방식(남은 후보 분야별 앞 4건)이 결정적이라 캐시 적중에 유리. 바꾸면 캐시 적중이 떨어질 수 있음 |
