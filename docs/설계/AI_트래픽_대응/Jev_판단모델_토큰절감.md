# Jev(초경량 판단 모델)로 생성형 AI 토큰 줄이기

> 작성 2026-11-24 Claude · 코드 미수정(설계만). 실측은 Korean 공고 3건 소규모 호출(아래 3장), 나머지 절감률은 추정이다.
> 관련: `AI_토큰_최소화.md`, `무료AI_토큰확보_조사.md`, 기존 구현 `web/lib/ai/jev.ts`(현재 웹 검색 결과 판정에만 사용)

## 1. Jev가 뭔지 (이 앱 관점)

- TypeSafe AI의 "System One" 판단 모델. **글을 쓰지 않고** 미리 정한 선택지 중 고르기(`choice`, 최대 255개), 예/아니오 확률(`noul`), 등급(`score`)만 돌려준다. 한 요청에 질문 여러 개를 묶을 수 있다. — [공식 API](https://docs.typesafe.ai/api/system-one.md)
- 가격: 입력 100만 토큰당 $0.042, **출력 무료**. OpenRouter 벤치에서 분류 1,000건 $0.025, 중앙값 194ms(같은 작업 GPT Luna $0.092·1.1초). — [OpenRouter 비교](https://openrouter.ai/blog/tutorials/jev-vs-llm-when-to-use-each/)
- 약점(공식·제3자 공통): **산술·개수 세기·날짜 비교에 약함**, 상태에 잡음이 많으면 정확도 하락, 저자원 언어에서 성능 하락. — [arXiv 평가](https://arxiv.org/abs/2609.37647)
- 무료 티어는 아니지만 사실상 비용이 0에 가깝다(공고 1,000건 태깅 ≈ 3센트, 3장 계산).

핵심 발상: **"판단"은 Jev, "문장"만 LLM.** 지금 LLM이 하는 일 중 상당수는 사실 분류·선택인데, 이걸 문장 생성 모델에 JSON으로 시키고 있어서 토큰이 크다.

## 2. 현재 AI 호출을 Jev로 바꿀 수 있는지

| 호출 (현재 LLM) | 본질 | Jev 대체 | 방법 |
|---|---|---|---|
| **동적 다음 질문 생성** (입력 최대 80,000자, 출력 1,800) | 어느 축으로 나눌지 **선택** + 질문 문장 | **대부분 대체** | 공고마다 축 태그를 미리 Jev로 붙여 두고(4장), 어느 축이 남은 후보를 가장 잘 나누는지는 코드가 계산. 질문 문장은 축별 템플릿·질문 승격 풀에서. LLM은 템플릿 없는 새 축일 때만 1회 쓰고 승격 풀에 저장 |
| **추가 탐색 질문 생성** (표본 24건·3,600자 + 지침 2,200자) | 같은 구조 | **대부분 대체** | 위와 동일. 선택지 후보는 태그 분포에서 바로 생성 |
| **공고 자격조건 구조화** (4,000자 입력) | 조건 종류 **분류** + 숫자 추출 | **부분 대체** | 대상(청년·무주택·학생·구직·1인가구 등)은 `noul` 묶음, 분야·고용형태는 `choice`. **나이·소득 숫자·마감일은 기존 정규식 규칙 유지**(Jev 산술 약점) |
| **근무지·주택 소재지 추출** | 지역 **선택** | **대체** | 1단계 시도 17개 `choice` → 2단계 그 시도의 시군구 `choice`(최대 255 이내). 상세 주소 문자열이 필요하면 기존 규칙 추출 |
| 분야 미표기 공고 재분류 | 분류 | **대체** | 직무군 `choice` + "직무 무관 일반 채용인가" `noul` |
| 다음 질문 후보 선택 (현재 호출자 없음) | 선택 | 대체 가능 | 후보 질문들을 `choice` 선택지로 |
| 웹 검색 결과가 실제 모집 공고인지 | 판정 | **이미 Jev 사용 중** | `lib/sources/websearch.ts` |
| 신청 준비 팁·초안 (1,200 출력) | 유형 판별 + **글쓰기** | 부분 | 신청 유형(온라인·방문·우편·이메일) `choice` → 유형별 체크리스트·순서는 템플릿. **초안 문장만 LLM** |
| 공고 쉬운 요약 | 글쓰기 | 불가 | LLM 유지(이미 공고별 영구 캐시) |
| 질문 문장 다듬기 | 글쓰기 | 불가 | 템플릿 정착 후 호출 자체를 제거 검토 |

## 3. 한국어 실측 (2026-11-24, `jev-latest`, 공고 3건 × 질문 4개)

| 공고 | 시도 choice | 분야 choice | "34세 이하 지원 가능" noul | "무주택자만" noul | 지연 |
|---|---|---|---|---|---|
| 셀트리온제약 생산직(충북 청주) | 충북 ✅ 1.00 | 생산·제조 ✅ 0.94 | 0.51 (나이 제한 없음 → 애매) | 0.02 ✅ | 318ms |
| 서울 청년월세(19~39세 무주택) | 서울 ✅ 1.00 | 주거 ✅ 0.99 | 0.89 ✅ | 0.96 ✅ | 165ms |
| 부산 해운대 카페 알바 | 부산 ✅ 1.00 | 알바 ✅ 1.00 | 0.73 | 0.03 ✅ | 175ms |

- 입력 합계 1,944토큰(≈ $0.00008). 공고 1건·질문 4개 ≈ 650토큰.
- 해석: **분류·지역·"적혀 있는가"형 질문은 한국어에서도 정확**. 나이처럼 숫자 추론이 필요한 질문은 애매(0.51) → 설계대로 숫자는 규칙으로 처리해야 한다.
- 표본 3건이라 정확도 결론은 아님. 적용 전 실데이터 100건 이상 정답셋으로 축별 정확도·신뢰도 임계값을 재야 한다(6장).

## 4. 제안 구조: "수집 때 태깅, 대화 때는 계산"

```
[하루 1회 수집(cron)]
 새·변경 공고만 → Jev 1요청(공고당 질문 8~12개 묶음)
   choice: 분야 / 시도 / 고용형태 / 신청유형 / 지원형태
   noul  : 청년대상 / 무주택요건 / 소득요건 있음 / 학생가능 / 구직자대상 / 1인가구 / 직무무관
 → 태그 + 확률을 공고와 함께 영구 캐시(Upstash)
 → 신뢰도 0.8 미만 축은 "미분류"로 두고 기존 규칙·LLM 폴백

[사용자 대화(질문 턴마다)]
 남은 후보의 태그 분포 → 코드가 정보량(가장 반반에 가깝게 나누는 축) 계산
 → 축별 질문 템플릿 / 질문 승격 풀에서 문장 선택   ← LLM 0회
 → 템플릿 없는 축만 LLM 1회로 문장 생성 → 검증 후 승격 풀 저장(다음부터 0회)
```

- 지금 구조와 같은 점: 축 기반 질문, 승격 풀, 후보 감소 검증은 이미 있다. 바뀌는 건 **축 분류를 LLM이 매 턴 80,000자 읽고 하던 것을, 수집 때 공고당 한 번 Jev로 끝내는 것**.
- 비용: 공고 1,000건 × 약 1,000토큰(질문 10개) = 100만 토큰 ≈ **$0.042/일**(새·변경 공고만이면 더 적음).
- 기대 절감(추정): 질문 턴의 LLM 호출이 "템플릿 없는 축"일 때만 남으므로, 질문 생성 LLM 입력이 **턴당 수천~수만 토큰 → 대부분 0**. 자격조건 구조화·근무지 추출 LLM도 Jev로 넘어가 무료 체인 한도(Groq 1,000회/일 등)는 요약·초안 같은 글쓰기에만 쓰인다. 실제 절감률은 usage 로깅으로 확인 후 기입.

## 6. 적용 전 확인할 것 / 위험

1. **정답셋 검증**: 실데이터 공고 100~200건에 축별 정답을 달고 Jev 정확도·신뢰도 분포 측정. 축마다 임계값(예 0.8) 확정. 임계값 미만은 "미분류"로 남겨 사용자에게 "확인 필요"로 보이게(오탈락 방지 원칙 유지).
2. **숫자·날짜는 절대 Jev에 맡기지 않는다**(나이·소득·마감일·금액). 실측에서도 나이 판단이 0.51로 흔들림.
3. 상태(state)는 제목·기관·요약·자격요건만 짧게. 잡음이 많을수록 정확도 하락.
4. Jev는 유료(초저가)·단일 회사 의존. 장애 시 기존 LLM 체인·규칙으로 폴백(현재 `judgeYes`처럼 실패하면 null).
5. 모델 버전 고정(`JEV_MODEL`)으로 결과 흔들림 방지, 버전 올릴 때 정답셋 재측정.

## 7. 구현 순서 (승인 시)

1. `lib/ai/jev.ts`에 `choice`·묶음 질문 지원 추가(지금은 `noul`만).
2. 수집 단계에 공고 태깅 + 캐시, 정답셋 측정 스크립트.
3. 근무지 추출·분야 재분류를 Jev 우선으로 전환(LLM 폴백 유지).
4. 질문 턴: 태그 분포 기반 축 선택 + 템플릿/승격 풀, LLM은 새 축만.
5. usage 로깅으로 전후 토큰 비교(`.ai-sync/compare/` 스크립트 재사용).

## 9. 재설계: 공고 DB에 칼럼으로 한 번만 저장 (2026-11-24, 사용자 요청)

원칙: 분류는 공고를 DB(공고 풀)에 처음 넣을 때 한 번. 이후에는 읽기만. 새 질문으로 새 칼럼이 생기면 그 칼럼만 한 번 더.

- 저장: `Opportunity.tags` = 칼럼별 값. 값 종류: 선택지 이름 / `""`(확신하는 해당 없음) / `"?"`(물어봤지만 확신 못 함 → 원문 단어 규칙). 키가 없으면 아직 분류 안 한 칼럼
- 분류 시점: `lib/server/pool.ts` 수집 저장 직전에만. 다시 모은 같은 공고(같은 id·제목)는 이전 DB 칼럼을 그대로 옮김(`carryTags`). 화면 요청·라이브 수집 경로에서는 분류하지 않음(이전 캐시 방식 제거)
- 빠진 칼럼만 질문(`missingQuestions`): 기본 칼럼 + 등록된 새 칼럼 중 그 공고에 없는 것만 한 요청에 묶음(최대 12개)
