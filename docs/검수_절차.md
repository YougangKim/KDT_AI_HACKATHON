# 마이뉴스 사용성 검수 절차

사람이 써 보고 지적하기 전에 같은 유형의 문제를 먼저 잡기 위한 검수 절차다. **기준은 항상 배포 사이트**(https://kdtaihackathon-web.vercel.app)이고, 실제 브라우저로 과업을 끝까지 수행한다. 로컬에서 고친 내용은 배포되기 전까지 "고쳐짐"으로 치지 않는다.

- 자동 검수: `cd e2e && node audit-live.mjs` (17항목, 약 2분, 다른 주소는 `node audit-live.mjs <URL>`, 결과 `e2e/artifacts/audit-<시각>.json`)
- 수동 검수: 아래 M1~M8 (약 15분, 1명)
- 채점: 만든 쪽이 아니라 Codex가 한다(`node .ai-sync/delegate.mjs codex "..." --review`). Claude는 점수를 매기지 않는다.
- 첫 실행 결과: `docs/검수_결과_20261122.md`

## 1. 근거: 업계 표준 방법 중 고른 것과 이유

| 방법 | 무엇을 재나 | 이 앱에 쓰는 방식 | 채택 이유 / 한계 |
|---|---|---|---|
| 과업 성공률(Task success) | 과업을 끝까지 해냈는가 | 페르소나 3명 × 핵심 과업 3개(결과 받기·좁히기·알림 저장) | 가장 기본 지표. 업계 평균 완료율은 약 78%(MeasuringU, 약 1,200개 과업) |
| 과업 시간(Time on task) | 걸린 시간 | 홈→결과 시간, 질문 수 | 보편 기준값이 없어 "30초 만에 시작" 문구와 질문 3~8개를 자체 기준으로 삼는다 |
| 오류율(Error rate) | 막다른 길·잘못된 결과 | 막다른 화면, 콘솔 오류, "아니오"라고 답한 지역 공고가 상위에 뜨는 건수 | 오류 수 / 오류 기회 수로 계산(UXtweak 정의) |
| Nielsen 10 휴리스틱 | 설계 원칙 위반 | M1~M5 수동 점검표로 압축 | 전문가 1명이 15분에 돌릴 수 있음. 실제 사용자 대체는 아님 |
| 인지적 워크스루(Wharton 외 1994) | 처음 쓰는 사람이 각 단계에서 막히는가 | 과업 단계마다 4질문: 목표를 세울까 / 올바른 행동이 보일까 / 그게 목표와 연결될까 / 진행됐다는 피드백이 보일까 | 사용자가 지적한 "추가 질문 버튼이 안 된다"는 2번 질문(버튼이 보이나) 실패 유형이라 이 방법이 맞다 |
| SUS(System Usability Scale) | 체감 사용성 10문항 | 마감 전 실제 사용자 5명에게 받을 수 있을 때만 | 평균 68점(Sauro, 약 500개 연구). 사람이 필요하므로 자동 검수에는 넣지 않고 기준 점수에서도 제외 |
| 데이터 충분성(앱 전용) | 질문·결과의 원재료가 충분한가 | 분야별 공고 수, 공고 조건 종류·분포, 링크 품질 | 이 앱은 "질문 다양성"이 공고 조건에서 나오므로 화면만 보면 원인을 못 찾는다 |

설치된 스킬 중 쓴 것: `ecc:browser-qa`·`ecc:e2e-testing`의 방식(실제 브라우저로 과업 수행, 산출물 저장)을 Playwright 스크립트로 구현. `ecc:click-path-audit`의 관점(모든 버튼이 눌렸을 때 실제로 상태가 바뀌는가)을 A9·A10·A11에 반영. `ecc:accessibility`에서 터치 영역 44px 기준만 가져왔다(A15).

출처: [NN/g 사용성 정량 평가](https://www.nngroup.com/articles/measuring-perceived-usability/), [MeasuringU SUS 해석](https://measuringu.com/?p=138), [UXtweak 사용성 지표](https://www.uxtweak.com/usability-testing/metrics/), [Wharton 외, The Cognitive Walkthrough Method](https://course.khoury.northeastern.edu/is4300sp13/ssl/articles/p381-wharton.pdf), [NN/g 인지적 워크스루](https://www.nngroup.com/articles/cognitive-walkthroughs/)

## 2. 페르소나와 과업

| ID | 페르소나 | 고르는 분야 | 답 규칙 |
|---|---|---|---|
| P1 | 서울 상경 취준생, 25세, 무주택, 1인 | 주거·채용 | 서울만 "예", 다른 지역 "아니오", 소득은 "모르겠어요" |
| P2 | 부산 알바생, 23세, 무주택 | 지원금·주거 | 부산만 "예" |
| P3 | 경기 사회초년생, 28세, 재직 | 선택 안 함 | 분야 질문은 "모르겠어요" |

과업: T1 홈에서 분야 고르고 결과 받기 → T2 "질문 더 해서 좁히기" → T3 분석 화면에서 왜 빠졌는지 확인 → T4 알림 저장(수동).

## 3. 체크리스트

### 자동(A1~A16 + A4b, `audit-live.mjs`)

| ID | 항목 | 통과 기준 | 잡는 사용자 지적 |
|---|---|---|---|
| A1 | 분야 여러 개 선택 | 누른 수 = 선택 표시 수, 게임 주소에 모두 전달 | ③ 여러 개 못 고름 |
| A2 | 고른 분야 재질문 없음 | 홈에서 고른 분야를 게임에서 다시 묻지 않음 | ⑥ 질문 품질 |
| A3 | 질문 다양성 | 전체 질문 중 지역 질문 ≤ 40% | ①·⑥ 질문 적고 단조로움 |
| A4 | 질문 수 | 첫 결과까지 3~8문항 | ① 질문 수 |
| A4b | 좁힘 효과 | 결과 ≤ 시작 후보의 50% | ① |
| A5 | 말투 일관 | 반말·존댓말 혼용 없음(AI 문장이라 2회 이상 돌린다) | ⑥ |
| A6 | 예측 수 정확 | "예면 N개" = 실제 남은 수 | 신뢰 |
| A7 | 결과 정합 | 상위 3개에 "아니오"라고 답한 지역 공고 없음 | 오류율 |
| A8 | 근거 투명 | 카드 근거에 분야 외 조건 1개 이상 | ④ 탈락·통과 이유 |
| A9 | 버튼 유지 | "더보기" 후에도 "좁히기" 버튼이 보임 | ⑤ 추가 질문 버튼 |
| A10 | 버튼 동작 | "좁히기" → 새 질문 → 결과 수가 실제로 달라짐 | ⑤ |
| A11 | 탈락 공고 열람 | 분석 화면에서 조건을 누르면 빠진 공고 제목이 보임 | ④ 질문별 탈락 탭 |
| A12 | 데이터 풀 | 고를 수 있는 분야마다 20건 이상, 0건 분야는 홈에서 비활성 | ② 공고 풀 작음 |
| A13 | 링크 품질 | 형식 오류 0, 기관 홈페이지 루트 링크 ≤ 10% | 신뢰 |
| A14 | 질문 원천 | 공고 조건 종류 6개 이상, 지역 조건 비중 ≤ 40% | ①·⑥의 근본 원인 |
| A15 | 모바일 | 390px 가로 스크롤 없음, 터치 영역 ≥ 44px(WCAG 2.2 AAA, AA 최소 24px) | 접근성 |
| A16 | 막다른 길 | 막다른 화면·콘솔 오류 0 | 오류율 |

### 수동(M1~M8, 15분)

| ID | 방법 | 확인 |
|---|---|---|
| M1 | 휴리스틱 1 시스템 상태 | 0건·조회 실패·출처 없음이 서로 다른 문구로 구분되나 |
| M2 | 휴리스틱 2 현실 언어 | "35세↑", "📍경기 ✕", "AI 생성 문장" 같은 내부 표현이 설명 없이 노출되나 |
| M3 | 휴리스틱 3 통제 | 결과 화면에서 답을 바꾸고 되돌릴 수 있나 |
| M4 | 휴리스틱 5 오류 예방 | 확실하지 않은 조건이 "딱 맞는 공고"로 표시되나 |
| M5 | 휴리스틱 9 오류 메시지 | 출처가 없는 분야를 고르면 원인과 대안을 말해 주나 |
| M6 | 인지적 워크스루: 좁히기 | 결과 → 더보기 → 좁히기의 각 단계에서 4질문 |
| M7 | 인지적 워크스루: 알림 저장 | 저장 → 알림함 → 삭제까지 4질문, 서버 저장 실패 시 안내 |
| M8 | 질문 품질 표본 | 질문 10개를 읽고 "청년이 실제로 답할 수 있나 / 결과를 바꾸나 / 이미 답한 걸 또 묻나" |

## 4. 운영 규칙

1. **언제**: 배포가 바뀔 때마다, 그리고 제출 전 마지막 1회. 로컬 수정만으로는 돌리지 않는다.
2. **순서**: 자동 → 수동 → 결과 문서(`docs/검수_결과_<날짜>.md`) → Codex 채점 → 고칠 목록을 수정 스레드로 넘김.
3. **통과선**: A1·A9·A10·A12·A16은 하나라도 실패하면 시연 불가(사용자가 바로 부딪힘). 나머지는 실패 수를 줄여 가는 지표로 쓴다.
4. **비결정 항목**: AI가 질문 문장을 만들기 때문에 A2·A3·A5는 2회 이상 돌려 한 번이라도 실패하면 실패로 본다.
5. **한계**: 자동 검수는 사람의 체감(SUS)을 대체하지 못한다. 페르소나 답 규칙이 단순해 "모르겠어요"가 많은 사용자, 키보드·스크린리더 사용자는 다루지 않는다. 알림 푸시 도착은 수동(M7)으로만 본다.

## 5. 다음 보강 (Codex 교차 평가에서 빠졌다고 지적된 검사)

- 키보드만으로 전 과업, 포커스 순서·표시, 스크린리더 이름
- API 실패·지연·빈 응답, 새로고침·뒤로가기·세션 복원, 알림 권한 거부
- 원문 링크 실제 목적지(HTTP 상태, 기관 첫 화면 여부), 공고 만료·중복·최신성, 분야별 지역 커버리지
- 상위 결과 정답률: 페르소나별 정답 공고를 사람이 정해 두고 상위 5개 적중 수 측정
- AI 변동 항목(A2·A3·A5)은 5회 이상 반복 실행
- 실제 사용자 5명 SUS와 과업 관찰(문제 발견용이지 통계적 일반화 아님)
